# Kai: implementation feasibility and integration map

Research date: 2026-09-24. Source of requirements: [`# Kai — Phase 1: Complete Research, Feas.md`](./%23%20Kai%20%E2%80%94%20Phase%201%3A%20Complete%20Research%2C%20Feas.md). This document covers every node in that outline. It is an implementation brief for a future UI build, not a claim that Kai already exists.

## Verdict and test environment

**Full one-to-one replication of the present ChatGPT/Codex desktop application inside the notch: No.** A robust **local Codex task client** is feasible. The ChatGPT Chat/Work project and conversation backend, all desktop artifact types, and the desktop voice experience do not have a documented third-party control/read API. Accessibility or AppleScript can help open or operate the desktop UI, but cannot provide a dependable background data model or lossless live stream. A separate OpenAI API agent would be a *new* product with separate sessions, not the user's existing ChatGPT conversations. [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Projects and chats](https://learn.chatgpt.com/docs/projects), [Agents overview](https://developers.openai.com/api/docs/guides/agents).

The checked host reports **macOS 14.2, build 23C30050t**, `arm64`, **Mac15,12**, 8 CPU cores, 24 GB RAM, and an Apple M3 GPU. Apple maps Mac15,12 to the **13-inch MacBook Air (M3, 2024)**. The OS reports `ReleaseType: NonUI` and the hardware overview labels the model/chip generically, so the exact screen geometry and permission prompts must be measured again in an ordinary logged-in GUI session. The installed desktop bundle is `/Applications/ChatGPT.app`, bundle ID `com.openai.codex`, version **26.917.71314**, build **10954**, minimum macOS **13.0**; its updater returned `up_to_date` on the production channel. The Homebrew CLI is **0.146.0**. A metadata-only App Server probe successfully read the active desktop Codex task; that task reported a newer producer `cliVersion` (`0.155.0-alpha.16.4`). **Do not assume the older CLI schema can round-trip every item written by the desktop host.** Generate bindings from the chosen binary and regression-test against representative desktop tasks before shipping. No content or account tokens were read in that probe. [Apple model identification](https://support.apple.com/en-gb/102869), [version-specific App Server schemas](https://learn.chatgpt.com/docs/app-server).

### Meaning of the columns

- **Clean?** `Yes` means a coherent Kai feature can be implemented with documented APIs on this Mac. `No` means the *exact existing desktop-app feature* cannot be replicated cleanly. A `No` row may still have an honest limited fallback.
- **Route** is the primary implementation surface: `App Server`, `Filesystem`, `Git`, `AppKit`, `Apple AX` (Accessibility/System Events), `Speech`, or `None`. Routes can be combined.
- **Scope/implementation** states exactly what the UI would show, the data operation to call, and the remaining boundary. The tables describe functionality, not visual styling.

## Recommended architecture and hard boundary

Build a signed macOS SwiftUI/AppKit menu-bar application. Use `NSStatusItem` as a reliable entry point and a floating `NSPanel` anchored immediately below the camera housing; read `NSScreen.safeAreaInsets`, `auxiliaryTopLeftArea`, and `auxiliaryTopRightArea` per display, and reposition on display/space changes. The physical camera cutout cannot display pixels. Do not hard-code the housing width or assume the same notch on an external display. [Apple NSStatusItem](https://developer.apple.com/documentation/appkit/nsstatusitem), [NSScreen safe areas](https://developer.apple.com/documentation/appkit/nsscreen/auxiliarytoprightarea-gr2n), [Apple camera-housing guidance](https://developer.apple.com/documentation/bundleresources/information-property-list/nsprefersdisplaysafeareacompatibilitymode).

Run a **Kai-owned `codex app-server` child process over stdio JSONL**. Send `initialize` with `clientInfo` and then `initialized`; correlate JSON-RPC request IDs, retain the read loop continuously, and dispatch notifications by `threadId`, `turnId`, and `item.id`. Use one writer queue and one reader task. Reconnect by restarting the process and reconciling with `thread/list`/`thread/read`; never assume a missed delta can be replayed. Choose a CLI version at least as new as the desktop task producer, generate its TypeScript/JSON schemas with `codex app-server generate-json-schema --out ...`, and gate experimental methods with `capabilities.experimentalApi`. The local stdio transport avoids the documented experimental/unsupported TCP WebSocket listener. Preserve Codex sandbox and approval decisions; handle server-initiated approval requests in the UI instead of silently granting them. [Protocol and transport](https://learn.chatgpt.com/docs/app-server), [approvals and item events](https://learn.chatgpt.com/docs/app-server).

The App Server exposes **Codex threads**, not a documented API for the desktop app's ChatGPT Chat/Work project graph. Kai should use a typed source model (`codexLocal`, `chatgptUnsupported`) and show honest availability, rather than blend unrelated conversation IDs. The Codex desktop tools visible to this research session (`list_threads`, `list_projects`, `read_thread`, etc.) are **agent-host tools inside this app**, not a public SDK or callable interface promised to a separate Kai process. Do not base Kai on their names, private desktop files/SQLite, copied auth tokens, undocumented endpoints, or injected JavaScript. [App Server scope](https://learn.chatgpt.com/docs/app-server), [desktop project model](https://learn.chatgpt.com/docs/projects).

`System Events`/AppleScript means GUI scripting, not Codex lifecycle events. The installed app bundle has a generic Chromium scripting dictionary for windows/tabs and no observed Kai-grade conversation/project command suite. macOS Accessibility (`AXUIElement`) can inspect/control exposed UI elements with user permission, but that surface is foreground, layout dependent, and may omit off-screen content. Use it only for explicit “Open in ChatGPT”/handoff affordances after testing, never for canonical history or background streaming. Codex **hooks** are a different mechanism: trusted lifecycle scripts can observe selected agent events, but they are not a replacement for App Server item streams and do not reconstruct old chats. [Apple AXUIElement](https://developer.apple.com/documentation/applicationservices/axuielement_h), [AX trust](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions), [Codex hooks](https://learn.chatgpt.com/docs/hooks).

## 1. Mode

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Mode selector | Yes | AppKit + App Server | Render the three requested destinations in Kai's own selector. Selecting `Codex` activates the documented local thread backend. Selecting Chat or Work must show unavailable/handoff state until a supported consumer backend exists; a selector is easy to draw but does not create backend parity. |
| ChatGPT → Chat | No | None; Apple AX handoff | Existing ChatGPT Chat history, project membership, creation, and streamed responses are outside the documented Codex App Server. An explicit button may activate/open the desktop app via `NSWorkspace`; AX click automation is an optional fragile handoff, not an embedded Chat client. A Responses API chat would create independent history and credentials. |
| ChatGPT → Work | No | None; Apple AX handoff | Work uses desktop/cloud orchestration, tools, files, plugins and artifacts. The App Server's Codex turn protocol does not document listing/starting/streaming the user's existing Work tasks. Link/open in desktop; do not label a new Agents API session as the same task. [Work overview](https://learn.chatgpt.com/docs/use-chatgpt). |
| Codex | Yes | App Server | Create or resume local Codex threads with `thread/start` or `thread/resume`, submit prompts with `turn/start`, and render `turn/*`/`item/*` notifications. It can read a known desktop Codex task on this host, but cross-version and concurrent-desktop-client behavior need a compatibility test. |

## 2. Projects

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| ChatGPT projects | No | None; desktop handoff | A ChatGPT project holds chats, uploaded files, sources and instructions, while local Codex `cwd` is a filesystem context. No documented consumer-project list/detail/mutation method exists in Codex App Server. Do not derive projects from private `~/.codex/.chatgpt-projects` state: it may be incomplete and is not a stable interface. [Projects and chats](https://learn.chatgpt.com/docs/projects). |
| Codex/local projects | No | App Server + Kai store | Kai can group tasks by directory in its **own** project catalog, but that will not be the exact desktop project identity, order, attached-folder set, or sidebar metadata. Persist Kai project IDs, primary `cwd`, optional secondary roots, and mapped thread IDs in Kai's store. `thread/list` offers `cwd` filtering for tasks. Label this “Kai local projects” until desktop project sync is supported. |
| Attached folders | No | Filesystem + Kai store | Let the user choose folders with `NSOpenPanel`, retain scoped bookmarks if sandboxed, and list/read them locally. `thread/start.cwd`/`turn/start.cwd` accept one working directory; the desktop's multiple attached folders and primary-folder discovery rules are a separate project model. Secondary folders may be referenced by absolute path only within actual sandbox permissions; do not imply they were attached to the desktop project. [Desktop attached-folder semantics](https://learn.chatgpt.com/docs/projects). |
| Repository | Yes | Git + App Server | For the primary folder, run `git rev-parse --show-toplevel`, `git status --porcelain=v1 -z`, and `git branch --show-current` through a controlled local `Process` or Git library. Group threads by normalized repository root/`cwd` and show the actual working tree. Resolve symlinks and handle non-repositories. Do not infer a desktop project ID from a Git root. |
| Worktree | Yes | Git + App Server | Detect `git rev-parse --show-toplevel` and `git rev-parse --git-common-dir`; use `git worktree list --porcelain` for siblings and map each worktree's path to threads' `cwd`. Worktree creation can use `git worktree add` after the user selects a branch/ref; keep separate working-tree status/diffs. The desktop's managed worktree registration/handoff is not a documented App Server operation, so this reproduces Git semantics, not its private management UI. [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees). |

## 3. Chats/tasks inside the selected project

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Existing chats | Yes | App Server | For Codex tasks, page `thread/list` with `cursor`, `limit`, `cwd`, `archived`, `searchTerm`; use `id`, `name`/`preview`, `createdAt`, `updatedAt`, and `status`. Join against Kai's own project catalog by normalized path. `thread/list` is not a ChatGPT Chat/Work list. If desktop task source metadata or grouping changes, show it as ungrouped rather than dropping it. |
| New chat | Yes | App Server | In a selected Codex local project, call `thread/start` with `cwd`, model and approved sandbox/approval policy; keep returned `thread.id`, then call `turn/start` for the first prompt. Use the exact generated schema for the installed binary. A new Chat/Work chat remains unavailable through this route. |
| Running status | Yes | App Server | Initialize from each `thread.status` (`notLoaded`, `idle`, `active`, `systemError`) and update from `thread/status/changed`, `turn/started`, `turn/completed`. Show `activeFlags` such as `waitingOnApproval` and final failed/interrupted state. Refresh list after reconnection because another desktop client may have changed tasks while Kai was offline. |
| Switching between chats | Yes | App Server | Changing selection changes the bound `threadId`. Call `thread/read(includeTurns: true)` for a passive view; call `thread/resume` to subscribe before sending or live-following. Dispose of old UI subscriptions with `thread/unsubscribe` when appropriate; never cancel an active task merely because the user changed views. The protocol's unsubscribe grace period is 30 minutes. |

## 4. Selected chat → Conversation

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Complete old history | Yes | App Server | For a normal stored Codex task, `thread/read` with `includeTurns: true` returns turns/items without resuming. Render every persisted `userMessage`, `agentMessage`, `commandExecution`, `fileChange`, tool and review item in recorded order. For large histories, `thread/turns/list`/`thread/items/list` provide pagination but are experimental and must be feature-gated; the docs warn existing paginated records may fail full-history read/resume. Unknown item variants must be preserved as generic cards, not discarded. “Complete” cannot be promised for unavailable ChatGPT tasks, ephemeral/deleted data, or future schema variants. |
| New output streamed live | Yes | App Server | On `thread/resume`/`thread/start`, keep the transport read loop active. Create cards from `item/started`, append `item/agentMessage/delta` by `itemId`, replace with authoritative `item/completed`, and finalize on `turn/completed`. Reconcile after disconnect with `thread/read`; do not treat deltas or `turn/diff/updated.items` as complete history. Cross-process subscriptions to desktop-started work should be tested with the matching desktop host version. |

## 4. Selected chat → Generated content

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Text | Yes | App Server | Render `agentMessage.text` by phase (`commentary`/`final_answer`) and streamed deltas; parse CommonMark/GFM for links, code blocks and tables. Use completed item text as final authority and sanitize external links. |
| Images | No | App Server + Filesystem | **Input** images are documented (`image.url`, `localImage.path`) and old `userMessage.content` can describe them. For **generated** images, App Server has no universal image blob/artifact retrieval contract in its common item union. If an assistant message references an accessible local image path or URL, validate and preview it; otherwise show the item/link and open it in the desktop app. Do not promise every native image-generation result will round-trip. |
| Files | No | App Server + Filesystem | Codex-authored files inside an accessible local workspace can be discovered through `fileChange.changes.path`, `turn/diff/updated`, and filesystem watch, then previewed by type. ChatGPT Work cloud files, attachments and desktop-only artifact records have no documented App Server download API. Keep origin/path/provenance and show unavailable when a file is not local. |
| Other artifacts | No | App Server + handoff | Markdown links and generic tool items can be represented as cards. Native desktop artifacts (for example specialized document, slide, browser, visualization or Sites panels) have no documented common schema that Kai can recreate one-to-one. Preserve raw item metadata for future adapters and offer “Open in ChatGPT” for unsupported types. |

## 4. Selected chat → Workspace

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| File tree | Yes | Filesystem | Enumerate the selected local root using `FileManager` or App Server `fs/readDirectory` with lazy loading; use `fs/watch`/FSEvents for invalidation. Respect hidden-file preference, ignore rules for performance, symlinks, sandbox permissions and path traversal. Remote/cloud task trees are a different backend and cannot be assumed local. |
| File preview | Yes | Filesystem + AppKit | Resolve the selected file under an authorized root; use `fs/readFile`/local reads for text, Quick Look or `QLPreviewView` for supported binaries, image/PDF renderers for common media. Cap size and reject unreadable paths. Preview reflects the actual workspace, not a snapshot of the exact file at an old turn. |
| Changed files | Yes | App Server + Git | During a turn, parse `fileChange` items and `turn/diff/updated` for agent edits. Outside a turn, compute current `git status --porcelain=v1 -z` and `git diff --name-status` to catch user/other-process edits. Keep “this turn” and “current working tree” as distinct labels; they can diverge. |
| Git diff/branch/worktree | Yes | Git | Use `git diff --no-ext-diff --` plus `git diff --cached --` for worktree/staged views, `git branch --show-current` (or detached HEAD hash), and `git worktree list --porcelain`. Render unified diff in Kai with rename/binary handling. `turn/diff/updated` is useful for the agent's aggregated turn diff, not a substitute for current repository state. |

## 4. Selected chat → Activity

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Terminal commands | Yes | App Server | Show each `commandExecution.command`, `cwd`, `commandActions`, `status`, duration and exit code. This covers commands represented as Codex items, not every terminal the user has opened elsewhere in the desktop app. For a Kai-owned terminal, use `process/spawn`/`process/outputDelta` or a PTY and keep its separate process handle. |
| Terminal output | Yes | App Server | Append `item/commandExecution/outputDelta` in arrival order, then replace/reconcile with `item/completed.aggregatedOutput`. Bound retained in-memory output and preserve full output only if available from the item; show truncation explicitly. `command/exec` has its own `command/exec/outputDelta` stream if Kai uses that API. |
| Tool activity | Yes | App Server | Render `mcpToolCall`, `dynamicToolCall`, `collabToolCall`, `webSearch`, `imageView`, `fileChange`, plan/review and unknown item types from `item/started`/`item/completed`. Display arguments/results with redaction and size limits; never infer secret text from hidden tool data. Show pending approval requests and send the corresponding JSON-RPC decision only from an intentional user action. |
| Current status | Yes | App Server | Combine `thread/status/changed`, `turn/started`/`turn/completed`, active item status, `turn/plan/updated`, warnings and approval state into one explicit state machine. `notLoaded` means the App Server has not loaded the task, not that a desktop task has finished. Use `thread/read` after reconnect to resolve uncertain state. |

## 4. Selected chat → Input

| Hierarchy feature | Clean? | Route | Scope/implementation |
| --- | --- | --- | --- |
| Type | Yes | AppKit + App Server | A focused text editor creates `{type:"text",text}` input. On an idle task call `turn/start({threadId,input:[...]})`; during a running turn, either queue the next turn or call `turn/steer({threadId,expectedTurnId,input:[...]})` for explicit steering. Show send errors and avoid duplicate submissions with a client request ID. |
| Paste | Yes | AppKit + App Server | Read text from `NSPasteboard`, preserve newlines, preview large input, and submit as text. Handle pasted images through the image attachment path. This is Kai's own pasteboard interaction, not a way to extract another app's transcript. |
| Attach file/image | No | App Server + Filesystem | Images are clean: validate a user-selected image and send `{type:"localImage",path}` or a supported image URL. An arbitrary file attachment is **not** a documented `turn/start.input` item type; for local Codex work, place/select a file under an authorized workspace and send a text reference to its absolute path. That is not equivalent to desktop ChatGPT file upload, especially for cloud Chat/Work. |
| Screenshot | Yes | ScreenCaptureKit + App Server | Capture a user-selected display/window/region with macOS Screen Recording permission, write to an app-controlled temporary PNG, preview it, then send `localImage.path` in a Codex turn. ScreenCaptureKit captures pixels, not hidden/off-screen app data; optionally pair with Accessibility text only when permission and UI support exist. The desktop's Appshots destination behavior is not exposed to Kai. [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [Appshots limits](https://learn.chatgpt.com/docs/appshots). |
| Voice | No | Speech + App Server | A practical **dictation-to-text** feature is feasible: request microphone and Speech Recognition permissions, capture audio with AVFoundation, transcribe with `SFSpeechRecognizer` (check availability/on-device support), place editable text in Kai's composer, then send ordinary `text` input. This does not recreate the desktop's voice call, audio stream, spoken replies, interruption, or ChatGPT Voice session. The documented App Server turn input list is text/image/localImage, not microphone audio. [Apple Speech](https://developer.apple.com/documentation/speech/sfspeechrecognizer), [App Server inputs](https://learn.chatgpt.com/docs/app-server). |

## Build contract for the next agent

### Minimal Codex wire recipe

Use these as protocol-shaped examples, then generate bindings from the actual shipping CLI version; the JSON-RPC 2.0 `jsonrpc` header is omitted on this wire. The `cwd` and `threadId` below are placeholders. [App Server lifecycle and examples](https://learn.chatgpt.com/docs/app-server).

```jsonc
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"kai","title":"Kai","version":"0.1.0"}}}
{"method":"initialized","params":{}}
{"id":2,"method":"thread/list","params":{"cursor":null,"limit":25,"cwd":"/absolute/project"}}
{"id":3,"method":"thread/read","params":{"threadId":"<id>","includeTurns":true}}
{"id":4,"method":"thread/resume","params":{"threadId":"<id>"}}
{"id":5,"method":"turn/start","params":{"threadId":"<id>","input":[{"type":"text","text":"Inspect this project"}]}}
```

In code, maintain `Map<threadId, TaskState>` and `Map<itemId, ItemState>`. On `item/started`, insert the item at its turn position; on `item/agentMessage/delta` or command-output delta, append only to that item; on `item/completed`, replace it with the final item; on `turn/completed`, set the final turn state. On reconnect, use `thread/read(includeTurns:true)` to rebuild state and de-duplicate by `turn.id`/`item.id`. Keep UI selection independent of subscriptions and execution. Handle server requests for approvals through an explicit pending-request queue keyed by request ID. This is an implementation inference from the documented event contract, not an OpenAI sample application.

1. **First milestone:** a Codex-only notch panel: list local tasks, select one, load full history, send/steer prompts, stream cards, show status/approvals, and reconcile after restart. Use a matched/newer Codex binary, generated schemas, stdio transport and real UI permissions.
2. **Second milestone:** local project catalog, folder tree/preview, Git and worktree views, screenshot/image input, and dictation-to-text. Keep Kai's project catalog explicitly separate from ChatGPT desktop project IDs.
3. **Parity gate:** before claiming Chat/Work parity, obtain a supported API for existing ChatGPT projects, conversations, task events, attachments and artifacts. In the current research, that gate is unmet. Do not fill it with private desktop databases, session cookies, undocumented network endpoints, or AX scraping.
4. **Acceptance checks:** compare a task created in the current desktop app and a Kai-created task in both directions; verify complete persisted history, concurrent live event delivery, interrupted/failed turns, approval prompts, image input, command output, and reconnect. Repeat after CLI/desktop updates. On macOS 14.2 test panel placement on the built-in notched display, external displays, full-screen spaces, menu-bar auto-hide, accessibility/screen/microphone permission denial, and sleep/wake.
